# ACNextGen Light Weight — V1.1.7-LW

ACNextGen Enhanced Physics の計算モデルを維持しながら、Luaアプリの値受け渡し・API取得・診断出力を軽量化した版です。



## 変更内容

- モジュール間の `ac.store` / `ac.load` を、共有Luaテーブルによる即時の値受け渡しに置き換えました。
- 同一更新内の同一オブジェクト・同一フィールド取得を共有化しました。CSPの未対応structフィールドは引き続き保護付きで取得し、nil・false・0を区別します。
- 外部公開は変更値のみをラウンドロビンで送ります。既定では各キーの公開間隔下限100 ms、一更新最大256回です。初期化時のみ全キーを公開します。
- 保存失敗は再試行し、Observerに失敗数を表示します。
- 多態的な共有ヘルパー4個だけにLuaJITのトレース境界を設け、過剰なトレース記録・中断を抑えました。ゲーム全体のJIT設定は変更しません。JIT制御が禁止された環境でも起動は継続しますが、性能結果はその環境で再確認が必要です。
- Observerにスクリプト更新のCPU時間（移動平均・ピーク）を追加しました。描画全体のフレーム時間やFPSではありません。

物理計算式、係数、モジュール有効/無効設定、実行順序、更新周波数は変更していません。
既存スケジューラのdt累積・上限制御も維持しています。今回のPRでは積分時間の修正や物理モデルの再設計は行っていません。
取得・保存ヘルパーを除く52モジュールの処理本体が元版と同じであることも確認しました。

## インストール

1. Assetto Corsaを終了し、既存の `assettocorsa/apps/lua/ACNextGen` フォルダを別の場所にバックアップします。
2. 配布ZIPの場合は、その中の `ACNextGen` を `assettocorsa/apps/lua/` に配置します。
3. GitHubから取得する場合は、作業ブランチの次のフォルダを丸ごと配置します。

   ```text
   ACNextGen_Enhanced_Physic/assettocorsa/apps/lua/ACNextGen/
   ```

4. Content Managerでアプリを有効にし、ゲーム内でACNextGen Observerを開きます。バージョンは `1.1.7-LW`、既定の表示モードは `balanced` です。

**Lua本体だけを差し替えず、modulesを含むフォルダ全体を差し替えてください。元版と軽量版を同時に動かさないでください。**
戻す場合はゲームを終了し、フォルダ全体をバックアップ版へ戻します。

## 外部連携がある場合の注意

このリポジトリで有効な処理は、主に車両情報を読み取り、追加モデルの状態と `ngp_*` 信号を計算・公開するものです。
AC本体へ直接タイヤ力などを適用する有効な経路は確認していません。FFB書き込みを含む `steering_mechanism` は元版と同様、既定で無効です。
したがって、ここで保証できる回帰検証の対象は内部モデルと出力信号であり、実車両挙動の実機確認ではありません。

既定の `balanced` では内部モジュール同士は即時に最新値を参照しますが、外部スクリプトが読む `ac.load('ngp_...')` の値は遅延します。
公開予算が混雑した場合は100 msより遅くなり、短時間の中間値は間引かれます。
このアプリが出力するキーへの外部からの上書きも内部計算には取り込みません。
アプリが出力しない外部入力キーは更新ごとに読み直します。

**車両側スクリプトや別アプリが `ngp_*` を物理入力として利用する、または同じキーへ書き込む場合は、互換モードを使用してください。**
`modules/ngp_core.lua` の設定を変更し、ゲームを再起動します。

```lua
M.performance = {
    mode = "compatible",  -- 既定値は "balanced"
    exportInterval = 0.10,
    exportBudget = 256,
}
```

`compatible` は取得・保存をその都度ネイティブAPIへ通し、外部上書きも参照します。通常の書き込みは公開間隔・予算で間引きません。
そのため外部連携のタイミングは維持されますが、`balanced` と同じ軽量化率は期待できません。
保存失敗時の保留値再試行は両モードで行います。

## 検証結果

比較元は、このリポジトリの `539f916` です。調査時点の Enhanced Physics のLua本体とも一致していました。

Linux / lupa 2.8 / LuaJIT 2.1、CSP APIはモックです。3000フレームを3回、ウォームアップ後に測定した中央値です。
毎フレームのUI呼び出しも含みますが、実際のUI描画・CSPのAPI実装・GPU負荷は含みません。

| 最終版の模擬測定 | 元版 | 軽量版 balanced |
|---|---:|---:|
| Lua更新CPU時間・通常テーブル | 3.7889 ms/frame | 2.3725 ms/frame |
| Lua更新CPU時間・未対応フィールドで例外を返すモック | 3.9165 ms/frame | 2.6148 ms/frame |
| ネイティブload呼び出し数・3000フレーム | 6,094,796 | 157,793 |
| ネイティブstore呼び出し数・同上・strictモック | 5,826,527 | 765,384 |

load呼び出しは約97.4%、store呼び出しは約86.9%減少しました。
模擬CPU時間は約33〜37%減少しましたが、この割合をゲーム内FPSへ換算することはできません。

回帰検証:

- 30 / 70 / 100 / 160 Hz、通常テーブルとstrictモックで、それぞれ1100フレームを実行。
- `compatible` も100 Hz / strictモックで1100フレームを実行。
- 車両・ホイール欠落、制動、操舵、クラッチ、変速、接触喪失、300 msの停止と復帰を含む合成入力を使用。
- 最初の長時間検証は5フレーム間隔等で34,436,196項目、診断表示を含む最終版は20フレーム間隔等で12,622,032項目を比較し、絶対/相対許容誤差 `1e-12` 以内で一致。
- 更新そのものは全フレーム実行。起動直後30フレームと欠落・復帰等の遷移点も比較。プロファイル時間、バージョン表示等の非物理診断値は比較対象外。
- Lua構文、実FFI cdataの未対応フィールド、キャッシュ寿命、nil/false/0、外部入力再取得、公開予算・公平性、保存失敗再試行、互換モード、JIT制御不可の単体テストを通過。

実機車両データ、外部連携、CSP固有のAPIコスト、実描画負荷はこのテストで再現していません。

### テストの再実行

履歴を含むGit cloneで実行してください。インストール用ZIPだけでは比較元コミットを取得できません。

```bash
python3 -m pip install --target .tools lupa==2.8
PYTHONPATH=.tools python3 tests/runtime_regression.py
```

最終確認と同じ条件:

```bash
PYTHONPATH=.tools python3 tests/runtime_regression.py --frames 1100 --snapshot-stride 20 --bench-frames 3000 --repeat 3
```

## 実機での合格判定

i7-8700 / RTX 3060 12 GB / RAM 16 GBで、同じ車両・コース・天候・台数・カメラ・解像度・CSP版・描画設定を固定してください。
アプリOFF、元版ON、軽量版ONを別セッションで測ります。ウォームアップ後、同じ60秒以上のリプレイ区間を各3回計測すると比較しやすくなります。
V-SyncやFPS上限が結果を隠さない設定で、平均FPS、1% Low、フレーム時間のスパイクも記録してください。

**100 FPS超えの合格判定はこの実測結果で行います。現時点では達成を保証・報告していません。**
未達の場合は、CSP版、車両/コース、外部連携の有無、各版のFPS、ObserverのScript CPU平均とNative export errorsを報告してください。
それにより、残っているゲーム固有の負荷と互換モードの必要性を切り分けられます。
